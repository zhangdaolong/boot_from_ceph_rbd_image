## Firmware implementation status

The current UEFI package has host-tested protocol code, a validated firmware configuration source, a Driver Binding protocol that maps the configured image, a read-only Block I/O publication path, and a CephX MAuth handshake driven from the messenger connect flow (including final AUTH ticket session-key parsing and AUTH ticket retention). A bounds-checked CRUSH decoder (`CephRbdCrush.c`) and OSDMap placement decoder (`CephRbdPlacement.c`) map object names to PGs and acting OSD sets; both are verified against vectors captured from a real cluster. A host-side live probe has validated, against a real Ceph 22 cluster: connect + CephX authentication + `MON_GET_MAP` + `osd getmap` (18-byte paxos header, `__s16` session_mon field) + object-to-OSD placement, decoding of primary OSD v1 endpoints, an authenticated primary OSD connection (OSD service-ticket CephX challenge + connect-time `SEQ` recovery), a **real `CEPH_OSD_OP_READ` returning the correct 16 bytes with `result=0`**, and the **full DXE BlockIo path** — RBD metadata discovery (`rbd.get_id`/`get_size`/`get_features`/`get_object_prefix` class methods) plus a data-block read, all over cached authenticated per-OSD sessions (`dxe_discover: status=0 ready=1 image_size=1073741824`, `dxe_read: status=0`). A GPT/ESP discovery module (`CephRbdGpt.c`) parses the protective MBR, GPT header (with CRC check) and partition entry array, identifies the EFI System Partition by its type GUID, and exposes the `\EFI\BOOT\BOOTX64.EFI` fallback path; the live probe validated it end-to-end against a GPT-formatted RBD image on Ceph 22 (`gpt_esp: status=0 esp_lba=6144-8192`) and correctly rejects a non-GPT image (`status=-4`). Note this requires the Ceph identity to carry the `class-read` cap (`allow r class-read`), not just `allow r`.

The DXE driver can now be built with a **real EDK II toolchain**: `bash scripts/build-edk2.sh` produces `CephRbdDxe.efi` (PE32+ EFI boot service driver) from `CephRbdPkg/CephRbdPkg.dsc`. The GPT/ESP → UEFI Boot Manager handoff (`CephRbdBootManager.c`) builds HD(GPT)+FilePath device paths, installs `Boot####`/`BootOrder` variables, and can optionally `LoadImage`/`StartImage` the x64 fallback loader; it is wired into the DXE driver behind `CEPH_RBD_CONFIG_FLAG_BOOT_MANAGER`/`TRY_BOOT`. Local IPv4 configuration (`CephRbdNetwork.c`) supports DHCP (platform default) and static station address/subnet mask via a separate `CephRbdNetworkConfig` UEFI variable. `KEY_REFERENCE` credentials are resolved through a platform secret resolver (`CephRbdSecretResolver.c`) backed by a protected UEFI variable. CephX now supports **AES-256-KRB5** (`CEPH_CRYPTO_AES256KRB5`: AES-256-CBC-CTS CS3 + HMAC-SHA384 truncated to 24 bytes) with 16/32-byte secret dispatch. The legacy BIOS stage2 can discover `!PXE`/`PXENV_UNDI` ROMs and send/receive raw Ethernet frames (`bios/stage2/pxe_undi.c`). The **full firmware-side boot chain is now validated end-to-end in an OVMF guest on the test cluster**: a network-enabled OVMF loads `CephRbdDxe.efi`, which authenticates to the monitor, maps the `boot-test` RBD image, discovers its GPT/ESP, registers `Boot0005`, reads `\EFI\BOOT\BOOTX64.EFI` from the ESP with a built-in FAT12/16/32 reader (`CephRbdEspFat.c`) into a buffer and starts it with `LoadImage`/`StartImage`. The guest serial log shows `CEPH_RBD_BOOTLOADER_STARTED`, proving a binary was executed directly from the Ceph RBD image with no host-side Ceph client. Remaining validation gaps are limited to full ARP/IP/DHCP + Ceph socket transport over BIOS UNDI and AES-256 live cluster validation.
