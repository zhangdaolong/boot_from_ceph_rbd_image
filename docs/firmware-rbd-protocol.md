# Ceph/RBD firmware protocol contract

This document separates the UEFI and BIOS firmware work into stable interfaces and explicitly marks elements that are not implemented yet.

## Implementation status

The package currently has bounds-checked little-endian wire cursors, bounded Ceph messenger v1 framing/connect negotiation/session sequencing, UEFI TCP4 transport, CephX payload codecs with AES-128 challenge-response, ticket decryption/validation and authorizer verification, Monitor/OSD RPC codecs with automatic reconnect on recoverable errors, a bounds-checked CRUSH decoder and OSDMap placement decoder, RBD Format 2 metadata discovery and read mapping, a validated firmware configuration variable, an `EFI_DRIVER_BINDING_PROTOCOL` that maps the configured image with per-monitor failover, and a read-only `EFI_BLOCK_IO_PROTOCOL` publication path. The BIOS directory has an independently testable MBR partition loader core. The v1 session handles framed messages, monotonic send/receive sequences, ACKs, duplicates, and keepalive tags; a bounded retransmit queue adds connect-time `SEQ` recovery and reconnect replay. The CephX MAuth handshake parses the final AUTH ticket session key and retains the AUTH ticket blob, and an OSD service ticket is requested and used to authenticate the primary OSD. The protocol layers (connect, CephX handshake, `MON_GET_MAP`, `osd getmap`, placement) are verified by host-side codecs/logic tests and by a live probe against a real Ceph 22 cluster; ticket decryption/authorizer verification, CRUSH and placement are additionally covered by real-cluster vectors. The live probe authenticates to the primary OSD and completes a real `CEPH_OSD_OP_READ` that returns the correct 16 bytes with `result=0`. There is still no EDK II build, OVMF integration, DXE `BlockIo` primary-OSD integration (read path still sends OSD ops over the monitor connection), GPT/ESP discovery, or BIOS PXE/control transfer. See [`boot-vm-from-ceph-rbd.md`](boot-vm-from-ceph-rbd.md). The BIOS PXE/control-transfer path is incomplete. Do not deploy this code to boot a production system.

## Bounded wire cursor

`CephRbdWire.c` provides safe little-endian integer reads/writes, bounded byte copies, and skips. `CephRbdMessenger.c` encodes/decodes fixed Ceph messenger v1 connect records, bounds optional authorizer bytes, classifies ready/retry/reset/wait responses, encodes complete v1 message frames, and decodes frames with aggregate-length and CRC32C validation. `CephRbdMsgrV1Handshake.c` performs the banner/address/connect exchange. `CephRbdMsgrV1Transport.c` sends encoded frames and reads one bounded message frame, rejecting unsupported tags, oversized payloads, and invalid headers. `CephRbdMsgrV1Session.c` assigns outgoing sequence numbers; validates incoming sequence order, ignores duplicates while re-ACKing, tracks peer ACKs, and handles ACK, CLOSE, KEEPALIVE, KEEPALIVE2 and KEEPALIVE2_ACK tags. `CephRbdMsgrV1Recovery.c` adds a fixed-capacity retransmission queue, bounded connect attempts that consume `RETRY_SESSION`, `RETRY_GLOBAL`, `RESETSESSION` and `WAIT`, connect-time `SEQ` recovery using `newly_acked_seq`, and reconnect replay of unacknowledged frames. `CephRbdRpc.c` adds a bounded failover runner: recoverable RPC reply errors (`EFI_TIMEOUT`, `EFI_CONNECTION_FIN`, `EFI_DEVICE_ERROR`, `EFI_NOT_READY`) reconnect the client and retry, while hard errors advance to the next monitor. Messenger v2 is not implemented. Message signatures are not verified (see `MSG_AUTH`/footer details below); the `CEPH_MSG_FOOTER_SIGNED` flag is accepted on incoming 13-byte legacy footers.

### Messenger v1 wire details required for a live OSD READ

The following were established against the Ceph 22 cluster and are enforced by the codecs:

- **Footer size.** `ceph_msg_footer_old` is 13 bytes (`front_crc`, `middle_crc`, `data_crc`, `flags`); the signed `ceph_msg_footer` is 21 bytes (adds a 64-bit signature before `flags`). Ceph selects the 13-byte form whenever `CEPH_FEATURE_MSG_AUTH` (bit 23) is **not negotiated**. Because the server's `features_required` can set bit 23 in the connect reply even when the client did not advertise it, the effective negotiated set must be `ConnectReply.Features & SupportedFeatures` (the bits sent in the connect frame). This driver never advertises `MSG_AUTH` and does not sign frames, so it uses the 13-byte footer and reads `flags` at footer byte 12 (vs. byte 20 for the 21-byte form).
- **Server-signed flag in the legacy footer.** The OSD calls `sign_message()` even though no signature is negotiated: it sets `CEPH_MSG_FOOTER_SIGNED` in `footer.flags` and then copies only CRCs + flags into the 13-byte `ceph_msg_footer_old`. Ceph's own receiver keeps the flag and sets `sig = 0`. The decoder therefore accepts the `SIGNED` flag rather than rejecting an otherwise valid reply; it does not verify signatures (the cluster has `cephx_require_signatures=false`).
- **`RESEND_ON_SPLIT` must not be advertised.** For legacy `MOSDOp` requests the OSD recomputes the placement seed from the object name and stores the full 32-bit Jenkins hash in `pg_t::ps`. When `CEPH_FEATURE_RESEND_ON_SPLIT` (bit 21, incarnation 2) is advertised, the OSD trusts that raw pgid and enqueues it directly, producing `4.1228e1dc ... no pg, shouldn't exist` and dropping the op. Leaving bit 21 clear makes the OSD route through `dispatch_session_waiting()` → `raw_pg_to_pg()`, which reduces the hash with `ceph_stable_mod()` against the pool's `pg_num`/`pg_num_mask` to the canonical PG (`4.1c`, pg 28, for `rbd_id.close-race-test`) and finds the primary OSD.
- **Legacy `MOSDOp` PG field.** `old_pg_t` / `ceph_pg` is `u16 preferred` (`-1`), `u16 ps`, `u32 pool` — not `u32 pool` + `u32 ps`. Encoding it incorrectly made the OSD decode pool 0.
- **`MOSDOpReply` v8 front layout.** HEAD_VERSION (`8`) encodes: `object_t oid` (`u32` len + bytes), `pg_t` (`u8` struct_v, `u64` pool, `u32` ps, `i32` preferred), `s64` flags, `i32` result, `eversion_t` bad-replay version (`u64` version + `u32` epoch), `u32` osdmap epoch, `u32` num_ops, `ceph_osd_op[]` (38 bytes each), `i32` retry attempt, then one `i32` rval per op. The returned READ bytes are in the message data buffer, not the front.

The firmware configuration blob must use a v1-enabled monitor port (6789), not the v2-only 3300. A complete client must implement v2 or explicitly negotiate/connect to a cluster endpoint with v1 enabled. `CephRbdTcp4.c` creates a TCP4 child on a selected UEFI TCP4 controller and can connect, send, receive, and close with per-operation timeouts; it uses the firmware's already configured IPv4 address. `CephRbdConfig.c` validates the fixed-size `CephRbdConfig` UEFI variable (FSID, up to four monitors, pool id, image, identity, key reference), and the DXE Driver Binding reads it to select a monitor.

`CephRbdCephX.c` parses version-1 server/authorizer challenges and response headers; encodes request headers, service-ticket requests, version-2 authorizer payloads, and version-3 authenticate payloads; bounds optional connection-secret parsing; and implements AES-128-CBC/PKCS#7 using Ceph's fixed IV and encrypted-payload wrapper for the challenge-response calculation. It also decrypts `CephXTicketBlob` payloads, parses `CephXServiceTicketInfo`/`AuthTicket`/`CryptoKey`, validates the global ID, caps and checks the timestamp window, rejects `allow_all` and non-AES-128 session keys, and verifies the authorizer reply's `nonce + 1` with optional connection-secret extraction. Only 16-byte AES keys are supported. AES-256-KRB5, ticket renewal, and a full multi-service authorizer exchange are not implemented; host vector tests verify the codecs and cryptography but do not establish interoperability with a live Ceph cluster.

## RBD striping map

`CephRbdFormat2.c` accepts already-decoded metadata, validates image size/order/features and either the default layout or striping-v2 parameters, then constructs `<object-prefix>.<16-hex-digit-object-number>` names. `CephRbdLayout.c` maps an image byte offset to one object extent. `CephRbdRpc.c` adds the `MON_GET_MAP`, `MON_COMMAND`, `OSD_OP` and `OSD_OPREPLY` codecs plus a synchronous reply-type-matched RPC call. `CephRbdCrush.c` parses the embedded CRUSH map (including straw2 buckets and the `TAKE`/`CHOOSE_FIRSTN`/`EMIT` rule steps) and reproduces Ceph's rjenkins string hash, `crush_hash32_2/3` and `crush_ln` algorithms. `CephRbdPlacement.c` decodes the target pool from an OSDMap front (`pg_num`, `pgp_num`, `crush_rule`, `object_hash`, `FLAG_HASHPSPOOL`) and maps an object name through PG and placement seed to its acting OSD set. `CephRbdBlockIo.c` fetches the canonical OSDMap via `MON_COMMAND "osd getmap"`, resolves `rbd_id.<name>` to an image id with `rbd/get_id`, then queries `rbd_header.<id>` with `get_size` (order then size), `get_features` (features then incompatible mask), `get_object_prefix` and, when striping v2 is enabled, `get_stripe_unit_count`. It then discovers a format-2 image, resolves each object's acting set through `CephRbdPlacement` and reads block ranges as bounded object reads. Discovery accepts a read-safe feature whitelist (layering, exclusive-lock, object-map, fast-diff, deep-flatten, journaling, striping v2) and rejects data-pool, migrating, non-primary, incompatible and unknown feature bits. The host-side live probe resolves the primary OSD, authenticates with an OSD service ticket, and completes a real READ (correct 16 bytes, `result=0`); however the DXE `BlockIo` read path still sends OSD ops over the monitor connection rather than reusing that primary-OSD client, and multi-pool data layouts, layered images with a parent, sparse/unwritten extents (a missing object fails the read instead of returning zeroes), snapshots and writes are not implemented.

## UEFI driver state machine

```text
Stopped -> Connecting -> Monitoring -> Authenticating
         -> MappingImage -> DeviceReady -> Stopped
```

`CephRbdDxe.c` implements this path in `CephRbdDriverInitialize()`: it connects the messenger client, discovers the image, fills read-only media (512-byte blocks), installs `EFI_BLOCK_IO_PROTOCOL` on the caller's controller handle, and returns `EFI_WRITE_PROTECTED` for write/flush. The DXE entry point now installs an `EFI_DRIVER_BINDING_PROTOCOL`; `Supported` accepts a controller when the configuration variable is valid, `Start` maps the image by trying each configured monitor, and `Stop` uninstalls Block I/O and closes the session. When the configuration sets `START_ON_ENTRY`, the entry point maps the image directly. Boot-manager/GPT/ESP discovery and OVMF validation are also outstanding.

## Security and protocol compatibility requirements

- Do not extend CephX cryptography from an informal description; use a vetted, compatible cryptographic implementation and test against supported Ceph releases.
- Never log Ceph keys or messenger session keys.
- Keep credentials in protected firmware storage and reject unauthenticated configuration updates.
- Reject malformed monitor, OSD, and RBD metadata lengths; cap all allocations.
- Authenticate each Ceph session using the negotiated CephX protocol.
- Fail closed on unsupported messenger features, image features, and striping layouts.

See `tests/rbd-layout-vectors.md` for deterministic layout vectors.

Run `sh tests/run-core-tests.sh` for native checks of wire bounds, CephX payload encoding and fixed AES-128 challenge-response/ticket vectors, messenger frame encoding against a fixed Ceph v1 wire vector (including the 13-byte legacy footer), frame integrity, retransmit-queue acknowledgement and retry limits, monitor/OSD request and reply codecs (including the `MOSDOpReply` v8 layout and `old_pg_t` field order), the RPC failover/retry policy, RBD header decoding and block-device bounds, Format 2 layout/object naming, configuration parsing/variable loading, Driver Binding Supported/Stop, and BIOS active-partition loading. The DXE sources are compiled against host stubs as part of this run. `sh tests/run-live-tests.sh` builds a host-side `live_probe` that exercises the real wire stack against a live Ceph v1 monitor/OSD: it validates connect + CephX authentication + `MON_GET_MAP` + `osd getmap` + placement + primary-OSD service-ticket authentication + a real OSD READ. These tests do not replace EDK II, OVMF, or end-to-end boot testing.
